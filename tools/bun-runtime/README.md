# Bun runtime provenance

`runtime.lock.json` fixes the exact official Bun v1.4.0 Android release assets and the unpacked executables used by this plugin. This is a pinned binary materialization workflow, not a claim that Gradle rebuilds Bun or JavaScriptCore from source.

The lock deliberately records two different Android boundaries. `minimumSupportedApi` is the plugin's tested product floor, currently Android 13 / API 33. Each artifact's `androidIdentApi` is the upstream ELF link target, currently API 28. The latter does not imply that the unmodified executable is portable to API 28-32 because those app seccomp policies can terminate Bun's raw `close_range` syscall with `SIGSYS`.

Run `node verify-runtime.mjs` before every build. On Windows, `materialize-runtime.ps1` downloads each fixed archive into a unique temporary directory, verifies its archive digest, copies only the `bun` executable into the controlled `jniLibs` path, verifies the unpacked digest and ELF layout, and removes the temporary directory.

The files are named `libbun_exec.so` solely so Android installs them into the read-only, executable `nativeLibraryDir`. They are PIE executables and must never be passed to `System.loadLibrary`.

The verifier checks the lock schema, repository-relative paths, cross-file minimum Android metadata, archive and binary hashes, ELF type and machine, `.note.android.ident`, interpreter, ordered system-library dependencies, and every `PT_LOAD` alignment. These are structural and provenance gates, not substitutes for execution on each supported Android version or on a real 16 KB page-size Android environment.

The separate `experimental/api28` directory contains the auditable source-build path for a future Android 9-12L experiment. Its immutable patch series, source/toolchain/registry/host-package locks, reproducible host image, two-ABI container build entry, binary hashes, ELF audit, corresponding-source lock, packaged Bun/WebKit license texts, and negative tests are intentionally isolated from the official artifacts. Two independent clean builds now produce byte-for-byte identical ARM64 and x86_64 executables, so the experiment reports `buildReady: true` and `runtimeProduced: true`; it remains `distributionReady: false` until a matching experimental APK passes the application-process gates and is actually published. The patched executables stay outside this repository and are not packaged by the current plugin. Direct adb-shell smoke passes on API 28 and API 31 are limited evidence, not application-process, Binder, APK, or general API 28-32 compatibility proof.

The `release` directory implements the distribution-source closure: three signed APKs are bound to the runtime hashes they contain, while the exact Bun, WebKit/JSC, native, Cargo, npm, and project sources are emitted as separate same-Release assets. Assets are deterministically split into parts of at most 1,900,000,000 bytes, safely below GitHub's 2 GiB per-file limit. A machine-readable manifest and `SHA256SUMS` cover every APK and source part. Publication first uploads a draft, compares GitHub's returned SHA-256 digest for every asset, and only then makes the Release public. The public license/relinking notice and these automated checks are technical records, not a legal opinion or approval.
