# M5 固定完整采样栈与内联调用者诊断

本批完成独立的 trace/inliner 观测工具、20 文件源码绑定和两种 x86 用户页大小的固定设备采集.
同一 92 输入 APK 在 API 36 / 4096 与 16384-byte 用户页各跑两轮, 共 8 个新 Bun 进程、
32 次 profile、2530 条采样 trace. 保存 65 份完整原始栈, 没有字节超限省略、采集失败或重试.
原门槛的五次 exit 0 和三次真实 exit 1 全部保留; 诊断采集完成不等于原压力套件通过.

四份完整 FTL 栈把目标语义帧明确关联到同栈的 `invoke` 机器帧, 两端名称/hash 同时匹配
编译器内联决定. 关闭映射的一段执行 5030 次目标调用, 64 条 trace 全无目标帧且均有
FTL 调用者. 这些是本批的新动态证据; 原始 2<3 DFG 样本失败的根因和稳定性仍未确定.

  `5c9d8b84a2e2ca03f8374b710f0e1262849ac057`. 预先存在的平台插件 1.8.0 设置保持不变.

  `0f966e81b78c84bb23213e391bc679c4ef83e56b`. 复用已有 90609496-byte 大页 JSC 候选,
  SHA-256 `17c7941a32669e0cf2d6915bf94d8cee8421c3df605eddcf2b493687f20e98a8`.
  Bun/WebKit/ICU 新构建均为零, 未恢复已清理的原生构建缓存.
- 新 [trace 工具](../../tools/bun-runtime/experimental/webkit-x86_64-16k/trace/README.md)
  的 JS 为原 restart 资产加三段标记观测代码. 去掉三段并按 LF 规范化后,
  每一字节都恢复为原资产. 热函数、invoke、参考算术、warmup、四个 profile 回调和门槛未改.
  这不意味着新资产整体与旧资产相同, 也不意味着新增观测没有运行时影响.
- 原 `validateRestartRecord` 不变, 仅显式绑定新资产 SHA-256
  `5c9b97009346ad8f422a1b2e3bb30c907cc0b44a2cdd598276e9a397477bc9ac` (11958 bytes).
  原七模式 pressure、sampling、restart、PC-map 的资产/Java/validator 和预算均保留.
  125 份受保护文件在前检与归档时逐字节一致.

两组共同启用 `dumpOptions=1`、`printEachDFGFTLInlineCall=true` 和
`collectExtraSamplingProfilerData=true`, 只有 `alwaysGeneratePCToCodeOriginMap=false/true`
不同. 第一轮 off/on, 第二轮 on/off, 每 arm 都通过实际生产 Binder 服务启动新 Bun 进程.
八份 stderr 的四项最终 JSC 选项全部通过严格核验, 请求环境单独保留.

每个进程仍为四段 300-ms/100000-call 工作循环、1000-us 采样间隔,
工作总时长上限 20s、Binder 超时 25s、源上限 16 KiB、stdout/stderr 合计上限 64 KiB.
300ms 是循环 deadline, 不是调度停顿下的硬墙钟上限; 本批回调约 300.005-309.582ms.
新增完整栈分类在每次 profile 返回后进行, 可能影响后续编译/分配/调度.

## 逐栈关联与固定保存上限

每段按六个互斥类别保存首次 trace: 目标 FTL 已关联、目标 FTL 未关联、调用者 FTL
但目标为其他层级、调用者 FTL 且目标缺席、目标/调用者 DFG 配对、其余.
每个首次候选限 4096 UTF-8 bytes, 所有见证合计限 24576 bytes; 计入完整序列化见证
及嵌套 JSON 转义. 超限就记录 oversize/budget, 不截断帧或改选之后更小的 trace.
缺席与省略分开记录, 所有 trace 仍进入有界计数.

本批每进程保存 14708-20275 bytes, 共 65 份原始栈, 没有省略.
实际 stdout/stderr 最大合计 30950 bytes, 未扩大原总输出预算.
主机重解析完整 trace 的所有帧, 校验类型/位置/层级/顺序、原直方图和时间范围,
再独立解析 `inliner` 与后方机器帧的名称和位置. 被保存的四条目标 FTL 关联如下:

| 用户页 | 轮次 / 阶段 | trace index (从 0 开始) | 目标位置 | inliner 与同栈 invoke 位置 |
| --- | --- | --- | --- | --- |
| 4096 | 1 / 1, map-on | 108 | `#EoFuS3:FTL:bc#57` | `#DawGsb:FTL:bc#92` |
| 4096 | 2 / 1, map-on | 62 | `#EoFuS3:FTL:bc#57` | `#DawGsb:FTL:bc#92` |
| 4096 | 2 / 4, map-on | 13 | `#EoFuS3:FTL:bc#69` | `#DawGsb:FTL:bc#92` |
| 16384 | 2 / 1, map-on | 85 | `#EoFuS3:FTL:bc#57` | `#DawGsb:FTL:bc#92` |

四条的目标帧位于 index 0, 机器帧位于 index 1. `inliner` 的 line/column 和机器帧
原值也完整保留. 两端 `jscPressureHotLoop#EoFuS3 -> invoke#DawGsb` 与同进程 FTL
内联决定匹配. 这里直接核验了四份原始栈; 夹具对全部 trace 统计的 90 条关联是另一层
汇总观察, 不能描述为另有 90 份独立导出的原始见证.

[固定源码补充](../diagnostics/2026-09-14-jsc-trace-source-review.md)说明这些字段来自 JSC
处理后的 CodeOrigin, 目标帧使用机器 code block 的 FTL tier. 这解释了 `noFTL(target)`
仍可出现目标名称的 FTL 语义帧, 因为目标自身的 FTL 编译限制与内联资格分开.
本批没有原始机器 PC、实际 map 指针或完整编译图, 也未用名称恢复把 FTL 改称 DFG.

开启组的 90 个目标 FTL 帧均被夹具关联到 `invoke`, 四份完整栈由主机独立重验.
关闭组的 84 个调用者 FTL 帧分布于三段, 相应 trace 都没有目标帧; 保存三份首条完整栈.
其余 trace 按原层级保留, 没有用累积编译计数代替样本.

4096 第一轮关闭组第四段: 目标调用 5030 次, trace 64 条, 目标全部层级和未知帧均为 0,
invoke FTL 64, 当前第四阶段仍在栈中. 前后 compiles/retries 都为 3/2.
该段首份完整栈中的调用者位置为 `#DawGsb:FTL:<nil>`, source line/column 原样为
4294967295. 该进程最终 exit 0 源于前三段累计达到原门槛, 不代表第四段目标采样正常.

第二轮关闭组另外两段是混合阶段. 一份缺席栈的调用者位置为 `#DawGsb:FTL:bc#127`,
另一份为 `<nil>`. 因而不能宣称关闭映射的每条调用者栈都缺少字节码位置, 或认定
每个缺席时刻的 PC 必定位于目标热循环内. 16384 第一轮开启组另有两条目标进入调用者
的 FTL 编译决定, 四段均没有 FTL 执行样本; 编译决定不提供完成或执行保证.
