# JSC PC映射关闭/开启: 固定对照与真实层级记录

本批完成M5的独立PC映射对照: 同一测试APK在API36原生x86_64的4KiB/16KiB用户页
各执行两轮, 完整收集8次进程诊断、32段profile和8份JSC最终选项回显.
4KiB开启组的三段profile累计记录155个目标FTL帧, 关闭组目标FTL为0;
两次开启运行因此按未改变的DFG门槛返回真实exit1. 收集成功与门槛通过分别保存.

本批没有重现上一批整段目标帧归零, 也没有复现或解释原压力程序的2<3失败.
本次观察支持PC映射影响内联目标名称恢复、恢复帧保留调用者机器tier的解释,
但不提供具体机器PC、map指针或逐帧CodeOrigin的直接观测.

4KiB第一轮开启组第四段执行10932次已检查的目标调用, 94条trace,
目标DFG0/FTL94、invoke FTL94、当前第四段帧94, 无直方图溢出或未知目标帧.
第二轮开启组第一段与第四段另有36/25个目标FTL帧. 对应进程都保留
`[InlineCall][FTL] Callee: jscPressureHotLoop#EoFuS3 -> Caller: invoke#DawGsb`.
原目标函数仍调用`noFTL`, 但该限制不禁止被内联到FTL调用者;
源码中的采样恢复逻辑将恢复的内联帧标为机器code block的tier.
因此这些目标FTL帧与原门槛不相容, 不改计DFG或把真实exit1改为成功.

关闭组4KiB第二轮第一/四段分别有8/4个invoke FTL帧, 目标FTL0,
但同段仍分别有13/39个目标DFG帧. 两段混合了不同优化状态,
不能用整个直方图断言每条FTL调用者栈的目标是否缺失, 更不能称为整段归零复现.
4KiB第一轮关闭组有FTL内联决定而无FTL采样;
16KiB第二轮开启组也有一次目标FTL内联决定, 四段仍未采到调用者或目标FTL.
内联日志来自编译过程, 没有逐段时间标记, 不能单独证明编译完成或该机器代码已经执行.

八次诊断的阶段/时间区间继续符合原restart/clear语义. 32段都有目标帧,
所以本批对[此前9766次调用但目标帧归零的现象](2026-09-14-m5-jsc-restart.md)
提供了相关的新选项/内联/层级证据, 没有在同一次固定对照中再次观察该完整现象.
原压力2<3失败没有逐次PC和trace细节, 不能由后来的不同夹具补齐它的事实.
